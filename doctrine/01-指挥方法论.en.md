# 01 · Command Doctrine (doctrine, revised as cases accumulate)

**语言 / Language:** [中文](01-指挥方法论.md) · [English](01-指挥方法论.en.md)

> When unsure, come back here; if here does not decide it either, rule on the spot by "reversible first + leave a trace", and file a case afterwards.

## 1. The ruling face (how to make decisions)

1. **Go with the default line, and put the ruling on the overturnable list**. Waiting for a decision is the most expensive kind of waiting; a wrong ruling is cheaper than no ruling — as long as ① it leaves a trace ② it is reversible ③ highest command can overturn it at any time. Only three kinds genuinely require stopping to ask: irreversible production surfaces, business facts only a human knows, outward-facing publication.
2. **Take grounds for a ruling in order**: the red-line text > an existing ruling precedent > system documents / the code artifact > my own inference. Skipping a level means writing "this part is inference" into the ruling.
3. **When two downstream parties report contradictory facts, the default explanation is an anchor-time difference, not that someone is wrong** — check each side's anchor artifact before ruling; until verified, believe neither side.
4. **When unsure whether something "should" be done, turn the question into "how do I undo it"**: if one command undoes it cleanly, just do it; if it does not undo cleanly, back up first; only if it cannot be backed up do you escalate.
5. **A list, a receipt or a memory handed to you is not a fact; the artifact is**. Spot-check on arrival: whatever one command can verify, verify on the spot (today's receipt-name reconciliation missed code that had already been built on <date>; code archaeology overturned my "never built" on the spot).

## 2. The scheduling face (how to use the fleet)

1. **The receipt is the only source of facts**; a window's self-report, a bus message and my own impression do not count. A state change must become a file.
2. **Dual-model pairing**: build → cross-review by another model; rework goes back to the original builder, re-review to the original reviewer (the review verdict is the acceptance baseline); a self-declared conflict of interest means swapping the person out.
3. **Only one workstation may be writing on the same branch** (rework is serial); reviews are always detached and anchored — later additions are not a violation, but the reviewed range must not move.
4. **Task-book token economy**: paste the context straight in, whitelist ≤5, exactly one verification command; carry the closing clause verbatim; choose the channel by the terminal you are in, two steps plus read-back; same harness uses the bus, and the criterion is the message entering the recipient's history.
5. **Dispatch the moment a window is free; always keep the next task book queued**; a waiter (a one-shot idle notification) is cheaper than polling, and event-driven is steadier than patrolling.
6. **Three things at the close of every task**: confirm the teardown is clean (ports/databases/accounts zeroed), roll the ledger + the sentinel roster, and put the good lesson into the SKILL / case book on the spot — overnight it is lost.

## 3. The risk face (how not to crash)

1. **The three-part kit for a risky action: back up → act → prove it**. Before touching a shared artifact, record its original state (the original git HEAD, the file byte count, a DB SELECT snapshot); for a restore-type operation, first establish "which version is the right one" before acting (the HEAD version is not necessarily right).
2. **A merge is done by the main window's own hand**: anchor to the sha that passed dual review, never chase the branch head; when resolving conflicts the default is a union that keeps both sides, and for a semantic conflict understand both intents before merging; after resolving it must compile. Closing a wave runs the gates (two frontend gates + the domain contract + the three menu gates + the default gate). Cross-line combination reds (each green within its own batch, red when merged) are exactly what the wave gate is for — characterise them case by case, do not rush to blame anyone.
3. **A criterion with no discriminability is not a criterion**. Before issuing any "green", ask: has it ever gone red? would it go red on the pre-change version? is the self-check a gate or a report?
4. **Better not to deliver than to misdeliver**; the read-back sampling window must cover the newline (the rule you set yourself is the one you are most likely to be caught by).
5. **Keep four monitors mounted: usage, disconnect, stall and receipts**; a monitor's own criterion must also be tested for discriminability (the `tail -3` disaster).

## 4. The growth face (how to get stronger)

1. Judgement overturned → file a case the same day; a lucky guess → file that too (an unrecognised piece of luck is next time's incident).
2. A case elevated into a rule goes into the SKILL (the fleet's statute); what stays here is the first-person process (case commentary).
3. First thing after a takeover/compaction: read 00-README + this document + the latest 10 entries of the case book.

## 5. The integration and batch-processing face (distilled from cases 30–41, <date>–<date>; the Owner ordered it written up on <date>)

1. **For an external system's enums, look at the real response payload before writing the mapping**. <external ERP> sends code B for "closed", not the Chinese words; code that maps on display text recognised not a single row against real data (case 40), and conversely treating what it cannot recognise as void is an incident (case 41). The task book must require "list the actual value range from a real response payload and give a mapping for every value"; passing against a mock does not count as passing.
2. **The default branch may only fall on the safe side**. "Unknown state → hold for a human / record the event only" is the safe side; "unknown state → void/cancel/complete" is the dangerous side (the failure direction of a guard, see [[feedback-guard-failure-direction]]). Any write-back path that automatically changes a document's status runs one round in observation mode on first release (record events only, touch no data); the main window checks the event counts before it is opened up; the morning after release you must check "event-table counts by type + the increment in cancelled/voided documents".
3. **The five-part kit for a batch-processing interface; missing any one means no merge**: a bounded entry point (limit / specified IDs), transactions per batch (commit per batch + a run record), an INFO log per batch, background execution that returns a runId immediately with progress queryable at /status, and no network calls inside a transaction. The first step on release is to run ≤3 rows of real data and watch them land, then the full set. For a long task with no progress signal the main window waits at most 30 minutes, then stops and adds an observation method rather than continuing to wait (7h20m with zero rows landed, case 40).
4. **"Merged ≠ released, released ≠ usable"**. The unit for judging project status is each document inside a module, not the task (Owner's correction on <date>, [[feedback-inventory-by-document-six-cells]]): backend / frontend / field wiring / document wiring / data as it stands / completion grade — five grades across six cells, all present, before it counts as inventoried. The task-receipt view only shows what was dispatched; it cannot show whether anything actually works end to end.
5. **Grep for the occurrences before relaying someone else's change request**. I compressed the reviewer's "add an independent variable" into "rename" and dispatched that (case 39) — for any rename/merge/delete instruction, if the symbol occurs in more than one place you may not write it from memory; either verify it yourself or quote the original text and mark it "this text governs". Once corrected, immediately deliver an override and order a rollback.
6. **Criteria and artifacts must use the same accounting, and the rules must not contradict themselves**. A criterion written in terms of "enum" while the artifact computes by "source" cost a reviewer a wasted round (case 34); two contradictory sentences in the same rulebook made two windows do opposite things, each following one of them (case 35). Before writing a criterion, look at how the artifact's field is computed; when the rules conflict, merge them into one sentence on the spot before dispatching.
7. **A pitfall in memory only counts as remembered once it is a gate**. "Two constructors missing @Autowired" was in memory and recurred exactly as before (case 36) → a Spring wiring smoke test became a hard criterion. The principle: a pitfall you rely on "remembering" will recur sooner or later; only a pitfall that "goes red when you run it" does not.
8. **A deploy-window switch written into the wrong namespace is the same as not switched on** (case 32): a new key first runs the orphan-key check (trace the key path back to a consumer); whether the gate is open is checked with a probe against the body, not against a 401; after deploying, pin the frontend to the same anchor, stop the old process and poll until the port is released, and only use -9 on timeout.
9. **A shared process is never started from `target/`** (case 30): repackaging the jar breaks the running JVM; every resident process uses only a copy under `run/` plus a start script that returns immediately (PPID=1).
10. **"Cannot find it ≠ it did not happen" must not be escalated into a report of real harm** (case 38): reporting real harm requires two independent pieces of evidence; a single empty query result may only be written up as "not observed". The same holds in reverse for verbal conclusions given to employees and to the Owner — acknowledge within seconds first, then verify, then answer ([[feedback-employee-msg-ack-first]]).
11. **Beyond a read-only reviewer's terminal state, read the "findings" too** (case 31): omissions in a production announcement often hide inside non-blocking findings; before merging, rule on every non-blocking item (absorb / small task / file a note) and do not let them vanish with the wave.
12. **Concurrent conflicts at the top of a document are normal**: several parallel tasks all insert a section at the top of implementation-plan, and during review any movement of the integration head gives rc=1. The disposition is to merge both sections into the current head in the candidate workstation; the conflict-resolution script must fail hard, and do not append add/commit on a newline after the assertion (the first time round it committed the conflict markers).

### <date> addendum: sweeping and closure
- **Define the sweep boundary by the failure surface, not by the lead**: following one parameter or one keyword to the end and then declaring the sweep complete will always miss something (the HPURGE first-review FAIL case). First ask "what things could connect to, or write into, somewhere they should not", then list every path that can reach there.
- **Closure does not rest on anyone remembering; it rests on a machine-readable table**: the whitelist/sweep table goes into the repo, the gate reads the table, a hit outside the table is red, and an expired row inside the table is also red (a whitelist that only ever grows is not a criterion).
- **When you set a rule, write its scope of application at the same time**: otherwise a builder treats another domain's hit as its own FAIL (RELCLOSE addendum 1), or treats out-of-scope as exempt.
- **Preservation and zero-change actions also need a non-empty criterion** (<date> ZOMBIE): the schema snapshot taken before dropping a database exported 16 lines of empty shells because zsh does not word-split — it was the criterion "a snapshot must contain CREATE TABLE" that caught it on the spot; otherwise we would have carried a fake snapshot into an irreversible action. Every "the backup is done" and "the export is done" must be able to answer "under what condition would it go red".
- **Guards in series: the right exit code does not mean it was this criterion that stopped it** (<date> HPURGE addendum 3): with several guards in series, the counterexample must verify that "the rejection reason came from the guard under test", otherwise it is a false green; the "restore and it must go red" step is the only way to expose this class of false green, and it may not be skipped.

- **The two diseases of a criterion (<date>, Crew J)**: always green (no discriminability) and red on day one for no good reason (historical data counted in) — they look opposite, and the cost is the same: nobody takes that criterion seriously ever again. Before writing a criterion, ask "under what condition would it go red", then ask "why is it not red / why is it red as things stand"; both answers must be sayable out loud before it ships.
- **A constant observable carries no information (<date>, Crew J's three examples)**: drift clearance that never clears, a heartbeat cycle that only ever accumulates, rerouted that is always 0 — whatever value it is constant at, it does not distinguish "the world is clean" from "the path is broken". Before every observable ships, ask "what would make it change", and record "proved discriminating in the sandbox" separately from "proved wired to the right place in production" — never read the former as the latter.
